# Examples

Everything in this directory is **synthetic**. It is generated by `jeval.synth`, which injects
a known miscalibration so the samples have something real to demonstrate. No production data,
no customer text, no cost figures from any real business belong here.

## Data

| File | What it is |
| --- | --- |
| `sample-decisions.jsonl` | 60 requests, two questions each, in raw ingest format. One question is deliberately overconfident. |
| `ingest-map.example.yaml` | The mapping that turns `sample-decisions.jsonl` into decision records. |
| `make-drift-log.py` | Writes the 1,800-decision log the README's `jeval drift` run is captured from. |
| `make-paired-log.py` | Writes the shadow-traffic log (900 requests, each answered by two versions) the README's `jeval drift --paired` run is captured from. |
| `service-quickstart.py` | A stand-in service with the two library lines, `collect.track` and `collect.resolve`: 600 decisions and 480 human answers. `docs/library.md` and `docs/instrumenting-a-service.md` quote its run. |
| `make-support-log.py` | Writes a two-version support-routing log in raw ingest format, for trying `jeval ingest` and `jeval drift` on a service-shaped log. |
| `ci/drift.yml` | A copy-paste GitHub Actions workflow that runs `jeval drift` and posts its summary. |

## The three surfaces

jeval has exactly three HTML surfaces a person looks at, and all of them are in this directory.
Each is one self-contained file: no JavaScript, no external request, nothing from the machine that
built it. Each is generated — never hand-edited — and the commands below rebuild them from the
repository root.

| File | What it is | Rebuild |
| --- | --- | --- |
| `report-example.html` | **The product report.** What `jeval report` writes, on the demo's synthetic log. The only surface a `jeval` command produces, and the file every number in the top-level README is checked against. | `uv run jeval demo --out-dir examples/report-example --seed 11 --scale 0.5` then `cp examples/report-example/report.html examples/report-example.html` |
| `demo-dashboard.html` | **The one-argument screen.** One screen, one claim: the threshold in use, the threshold the cost minimum points at, both drawn and named on the same chart, the 95% interval drawn as a band, the confidence distribution underneath, and the drift gate's verdict as a word at the top. Laid out as a technical report: one left-aligned column, small title, hairline rules, native `<details>` for the small print. No scrolling on a 1440×900 window. | `uv run python examples/make-demo-dashboard.py examples/demo-dashboard.html` |
| `workbench.html` | **The workbench.** Both of the above on one page: a kicker, an index of anchors, the one-argument screen inside the first 900px, then the full report folded into a native `<details>` as an inline frame whose document is read from `report-example.html` at build time. One file that answers "show me everything" without a second window. | `uv run python examples/make-workbench.py examples/workbench.html` |

The screen and the workbench are not jeval commands and not product surfaces — the product writes
one report, and a dashboard is explicitly out of scope. They are presentations of the same code's
output: every figure is computed by the library (`evaluate`, `sweep_actions`, `build_impact`) on
the same synthetic dataset and the same cost matrix `jeval demo` uses, so the three files can be
compared line by line.

### Rebuild order

The workbench inlines the report at build time, so it inherits nothing live. After any change to
the report's stylesheet, charts or data, rebuild in this order and then run the tests:

```sh
uv run jeval demo --out-dir examples/report-example --seed 11 --scale 0.5
cp examples/report-example/report.html examples/report-example.html
uv run python examples/make-demo-dashboard.py examples/demo-dashboard.html
uv run python examples/make-workbench.py examples/workbench.html
uv run pytest -q tests/test_readme_example.py tests/test_demo_dashboard.py
```

`tests/test_readme_example.py` requires the README's quoted numbers and size claim to match
`report-example.html`; `tests/test_demo_dashboard.py` rebuilds `demo-dashboard.html` and requires
a byte-for-byte match, one `<h1>`, both thresholds named in words, and no `<script>`.

### Design language

All three share one design language, and the report's stylesheet
(`jeval/report/assets.py`) is where it is written down:

| | |
| --- | --- |
| **Surfaces** | warm paper `#f7f6f2` with white plates for charts; dark mode is its own palette (`#141412`), not an inversion |
| **Type** | a serif for the title and section headings (Iowan Old Style, Charter, Cambria, Georgia), a sans for everything read (Inter, SF Pro, Segoe UI, Roboto), and a mono only for identifiers and code. No web font: each stack names the best face a reader is likely to have and falls through to the platform's own |
| **Scale** | 13 / 14 / 15.5 / 17 body / 19 / 28 / 30 / 40 px, and 40 px for a headline figure; chart labels 12.5-13 px, drawn at the chart's own size and never stretched |
| **Numbers** | tabular lining figures in the sans face, right-aligned; money in the currency's own decimals (`KRW 38,524,590`, `USD 1,926.23`) from `jeval.currency` |
| **Findings** | each section states its result as a sentence in the serif, then draws it: figure cards with the figure they replace struck through, said-versus-right rows, one verdict card per action, progress bars for labels, one composition bar for the log |
| **Tables** | never the first thing a reader meets: folded under "The numbers behind this, as a table". Inside, sentence-case headers over a heavier rule, hairlines between rows, text left and numbers right |
| **Colour** | greys for data; blue `#1f5fbf` for the line the report recommends and vermilion `#d1491f` for the line in use, a pair validated for colour-vision deficiency (CVD delta-E 24.6 on white). Neither is ever the only signal: every mark is also named, dashed or solid |
| **Charts** | inline SVG with `<title>` and `<desc>`, no y-axis spine, labels placed where the curve leaves room, and a status word (`PASS`, `FAIL`, `Threshold too low`) wherever a colour states a verdict |

## Run the sample

```sh
mkdir -p /tmp/jeval-sample && cd /tmp/jeval-sample
jeval init
jeval ingest /path/to/jeval/examples/sample-decisions.jsonl \
  --mapping /path/to/jeval/examples/ingest-map.example.yaml
jeval report --by lang
```

The sample is small on purpose: 120 records cannot support a firm calibration claim, and the
report will say so through wide confidence intervals. That is the point — a small sample is
exactly the situation where people read too much into a bin.

For a larger, self-contained run, use `jeval demo`, which generates a few thousand records
across four questions with different failure modes. The screen and the workbench run on two model
versions of those four questions, so the drift step has something real to compare: the candidate
is deliberately overconfident, and the drift gate fails on it.
